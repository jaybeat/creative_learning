# 一节怎么编排：拆概念清单，选原子方法

**适用范围**：写一节书稿之前先做这一步，不分概念类型。

**和其他方法的关系**：本文只管"一节里讲哪些概念、按什么顺序、各用什么方法"，以及开场和场景。每个概念具体怎么讲，见对应的原子方法。

**证据**：规则来自 Gauth 集合课和 2.1，完整案例见文末"范例"。

---

## 一、拆概念清单

一节通常不是一个概念，而是**一个核心概念加几个关联概念**。骨架的大部分结构是由这些关联概念撑起来的。

1. **列出这一节要讲的所有概念**：核心概念、它的特性、术语和记号、表示法、要学会的判断或转换。
2. **按依赖关系排顺序**：后一个要用到前一个。
3. **给每个概念判断类型，选方法**（见第二部分的两步判断）。
4. **决定哪几个概念各自成为一个知识单元**。特性、术语这类组成部分，嵌在核心概念里讲；判断、转换这类要学会做的事，各成一个单元。
5. **练习检验最后一个单元**，前面的单元由它顺带检验。

**清单的样子**（2.1 线性表）：

| 概念 | 类型 | 单元 | 方法 |
|---|---|---|---|
| 线性表 | 约定 × 是什么 | 线性表 | deductive |
| 记号 aᵢ、长度、前驱、后继、空表 | 术语、记号 | 嵌在线性表里 | deductive |
| 同类型、一个接一个、个数有限、可以重复 | 特性 | 嵌在线性表里 | deductive |
| 判断能不能看成线性表 | 判断（"是什么"自带） | 线性表 | deductive 的判断例题 |

有"怎么做"单元的清单（Gauth 集合课：集合 + 列举法）见 `docs/course/ref/gauth-sets.md` 第二部分。

## 二、知识类型 → 方法：两步判断

分类看知识类型，不看它在数学上算什么。

**第一步：约定还是发明？** 决定用哪种框架。
- **约定**：人为规定的语言、模型、操作，没有一个问题能逼出它。用**演绎框架** `deductive.md`：先命名，再具体化。场景里的问题只用来引出需要。
- **发明**：为解决一个真实问题想出来的办法，问题会把它逼出来。用**推导框架** `derive.md`：总名字可以先预告，部件推出来之后再命名，最后讲得失。

拿不准时问："能不能从一个问题和它的约束，一步步推出这个东西？"能推出来，就是发明。

**第二步：是什么还是怎么做？** 决定怎么具体化。
- **是什么**：用实例加最小对照；
- **怎么做**：完整做一遍。

| | 是什么 | 怎么做 |
|---|---|---|
| **约定**（演绎） | 集合、线性表（2.1） | 列举法、交集、并集、线性表的基本操作（2.2） |
| **发明**（推导） | 顺序存储、链式存储、头结点（2.3、2.9、2.14） | 顺序表插入为什么从最后一个开始挪（2.4）：推测。没有经典证据，`derive.md` 不覆盖，暂时用写法库第 5 条 |

一组操作（操作集）不是一种新类型：它是几个"怎么做"的组合，每个操作按它所在的格子写。

## 三、开场

开场写在一段课程的第一节，或者章首引言里。段内其他节不另设开场，问题页开头用一句话回扣开场的第几问。

1. **场景**：读者每天都见到的东西。
2. **从场景里指出一样具体的东西**，它正好是核心概念的实例。
3. **点名**：这样的东西叫 X。由大到小，读者在听到名字之前已经看到了它指的是什么。（约定类的点名写法见 deductive）
4. **学完能做什么**：一句话，写本事，不写场景里的任务。
5. **一段课程的第一节，再加几个挂起的问题**，加一句"先记住，从第一个开始"。小问要满足三条：
   - 具体到读者能先猜一下；
   - 每个都有确定答案，并且在这一段课程里答完；
   - 不提前摆出后面才会冒出来的问题。

**易错**：
- 问题的答案就是概念名本身；
- 学习目标写成场景里的任务，比如"做出编辑器"；
- 整章挂一个顶层问题，会悬挂太久，还会剧透后面的发现。

## 四、场景怎么选

1. **读者每天都见到**，不用解释就懂。
2. **场景里有一样东西正好是核心概念的实例**，能直接指着说"这样的东西叫 X"。
3. **能承载关联概念和后面几节的内容**，比如一行字能带出插入、删除、放进内存。
4. **场景是检验台，不是学习目标**。

**场景贯穿主线，但不包办一切。** 开场、问题、定义的第一个实例放在场景里。对照、例题如果在场景里做不干净，就换更干净的材料：
比如 2.1 的反例换成了家谱，因为一行字永远是线性表，场景里给不出反例。
