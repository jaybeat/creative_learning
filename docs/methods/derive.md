# 推导框架：介绍发明出来的办法

**适用范围**：为解决一个真实问题、在约束下**发明**出来的结构或表示，比如链表、链式存储。判断问题："能不能从一个问题和它的约束，一步步推出它？"能推出来，就用本框架。

**和其他方法的区分**：
- 人为规定的约定（集合、线性表、交集、并集）用 `deductive.md`。演绎框架是先命名、没有得失；推导框架是先推出来、后给部件命名，有得失。
- "发明 × 怎么做"（比如插入为什么从后往前挪）目前没有经典证据，本框架不覆盖，暂时用写法库第 5 条。
- 一节怎么编排见 `plan-section.md`；写作要求见 `narration-ready.md`。

**证据**：只依据 Harsha（mycodeschool）的链表入门课，分析见 `docs/course/ref/harsha-linked-list.md`。本书还没有按本框架核对过，用过一次后更新。

---

## 一、目标

让读者知道这个办法**为什么存在、是怎么被逼出来的、换来了什么、付出了什么**。读者在听到部件的名字之前，已经体会过它要解决的问题，也跟着走过推出它的每一步。

## 二、骨架

| 步 | 做什么 | 例子（Harsha） |
|---|---|---|
| 1. 交代逻辑 | 一句话：要理解新办法，先看旧办法的局限 | 要理解链表，先理解数组的局限 |
| 2. 模型和约束 | 搭一个能推理的模型，把约束写成规则 | 内存是带地址的格子；位置由内存管理员分配，旁边可能已经给了别人 |
| 3. 旧办法 | 在模型里演一遍旧办法，先讲它的好处 | 数组是连续一块，按下标算地址，常数时间访问 |
| 4. 问题 | 从一个具体需求里自然冒出来；把出路逐条走完，落到两难 | 再放一个数 → 不能原地加长 → 另开一块再复制 → 开大浪费、开小又要复制 |
| 5. 推导 | 一条因果链：改动 → 直接后果 → 新问题 → 补救 | 一次只要一个 → 不相邻 → 不知道谁第一 → 每块记下下一块的地址 |
| 6. 命名和收拢 | 部件推出来后才命名，立刻落成定义或代码；一句定义加直接推论；两种视图对照 | "这块叫结点"，`struct Node`；只要记住头结点，只能从头走 |
| 7. 检验 | 用新办法实际做一次 | 在末尾加一个 3 |
| 8. 得失 | 和旧办法逐项对照；最后一条回答开头的问题 | 访问 O(n)；插入也是 O(n) 但不用挪；不用事先猜大小 |

## 三、细则

### 1. 交代逻辑
- 开头一句说清这一课的逻辑：新办法要靠旧办法的问题来理解。读者一开始就知道后面是"旧办法不够用 → 新办法"。

### 2. 模型和约束
- 先搭一个能在上面推理的模型，比如带地址的内存格子。
- 后面推导要用到的约束，都在这里写成规则，比如位置由别人分配、相邻的地方可能已经被占。没有约束，办法就不是"被逼出来"的。
- 约束可以拟人化，比如"内存管理员"，把规则变成对话。这只是手段，可用可不用；约束本身必须讲清楚。

### 3. 旧办法
- 在同一个模型里演一遍旧办法，**先讲它的好处**，比如常数时间访问。这样后面比较得失才公平。
- 旧办法的工作原理要讲到够用：后面补救时要参照它（数组靠位置算出顺序）。

### 4. 问题
- 问题从一个具体需求里自然冒出来，比如"再放一个数"，不是作者宣布"数组有缺点"。
- 把能想到的出路逐条走完，每条都说清为什么不行或代价是什么，最后落到两难。走到无路可走，读者自己就想要一个新办法。

### 5. 推导
- 可以先预告总名字，比如"这个问题的解法叫链表"，当作要去的目标。部件的名字留到推出来之后再给。
- **每一步 = 一个改动 + 它的直接后果**，比如"一次只要一个"→"大概率不相邻"。
- **新做法带来的新问题，用一个改动补上**，比如"不知道谁第一"→"记下下一块的地址"。整段推导是"改动 → 后果 → 新问题 → 补救"的链条。
- **每一环都有因果**。不能是作者先知道答案、再挑出来的"观察"。
- **补救参照旧办法**：旧办法靠什么做到这件事？新做法丢了它，所以要把它明着记下来。
- **边界情况在推导里顺手解决**，比如最后一块没有下一个，写 0。

### 6. 命名和收拢
- 部件推出来之后才命名，一句一个，回指刚推出的东西："我们把这块叫结点。"
- 命名后立刻落成定义或代码，比如 `struct Node { int data; Node* next; }`。
- 收拢成一句定义，再加上从定义直接推出的结论，比如"只要记住头结点；只能从头一个个走"。
- 两种视图对照：模型里的真实样子（内存地址）和逻辑上的样子（箭头）并排，说明是同一个东西。

### 7. 检验
- 用新办法实际做一次操作，证明它真能用，比如在末尾加一个元素。

### 8. 得失
- 和旧办法逐项对照：访问、插入、删除、空间。
- 复杂度相同的，要说清差别在哪，比如插入都是 O(n)，但链表不用挪动。
- 代价可以用生活比喻帮助理解，比如寻宝游戏：只能问到一个、才知道下一个在哪。
- **最后一条回答开头的问题**，比如"不用事先猜大小"，让问题和答案闭环。

### 贯穿全程
- 同一组数据从头用到尾，地址都用具体数字，比如 6、5、4、2，后来加 3、插 10。

## 四、易错

- **先给定义再推导**：读者还没体会到问题，定义是空的。
- **推导跳步**：某一步没有因果，读者跟不上，只能记结论。
- **旧办法只讲坏处**：得失比较不公平，读者也不知道新办法放弃了什么。
- **得失没有回到开头的问题**：闭环断了，读者不知道最初的问题解决了没有。

## 五、自检

- [ ] 能从问题和约束一步步推出这个办法（不是约定）。
- [ ] 模型里写清了推导要用的约束。
- [ ] 旧办法先讲了好处。
- [ ] 问题从具体需求自然冒出，出路逐条走完。
- [ ] 推导每一步都是"改动 → 后果"，新问题都有补救，没有跳步。
- [ ] 部件推出来后才命名，命名后有一句定义和直接推论。
- [ ] 用新办法做过一次。
- [ ] 得失和旧办法逐项对照，最后一条回答了开头的问题。
