# 讲解写法库

这里收集写书过程中和作者一起定下来的讲解写法：每种写法讲什么、适合什么样的知识、什么时候用、怎么写、容易写坏在哪里。写新的一节（不限第2章）之前，先在速查表里找知识类型，挑写法。

第2章具体怎么改、改到哪一步，见 `docs/ch02-revision-guide.md`。本库只收跨章节可复用的写法。

## 怎么积累

- 作者在讨论中认可了一种新写法，改完那一节后，在这里加一个条目。
- 作者否决了一种写法，在对应条目的"否决过的写法"里补一条，写清原因。
- 同一种写法有了新的范例，只在"范例"里加出处，不重复建条目。
- 条目格式固定：适合什么知识 / 什么时候不用 / 骨架 / 范例 / 要守住的点 / 否决过的写法 / 来源。

## 速查：知识类型 → 推荐写法

| 要讲的知识 | 例子 | 推荐写法 |
|---|---|---|
| 对已有事物的抽象（第2层概念） | 线性表、抽象数据类型 | [演绎式](#2-演绎式先点出概念再逐条讲) |
| 解决某个问题的办法（第2层概念，带第3层"为什么"） | 顺序存储、链式存储、动态数组 | [推出办法再命名](#1-推出办法再命名) |
| 同一样东西有具体和简化两种画法 | 内存格子图 ↔ 链表箭头图 | [两种画法对照](#3-两种画法对照) |
| 一种数据表示刚讲完，要证明它真能用 | 把 cat 放进顺序表、存进链表 | [概念讲完，立刻做出第一个实例](#4-概念讲完立刻做出第一个实例) |
| 会改变数据状态的操作、算法（过程性知识） | 插入、删除、销毁 | [一个问题，一步一图](#5-一个问题一步一图) |
| 一个操作有几种情形 | 插在第0个 / 中间 / 末尾 | [情形由简到繁](#6-情形由简到繁不需要新代码的一句话并入) |
| 从例子得出通用代码 | 任何"写成函数" | [先具体后一般](#7-先具体后一般) |
| 代码里有读者第一次见的语法 | `*L`、自引用结构体、typedef 指针 | [语法细节放说明框](#8-语法细节放说明框) |

## 1. 推出办法再命名

**适合什么知识**：概念本身是"为了解决某个问题而想出来的办法"，例如顺序存储、链式存储、动态数组。读者先有了"解决了问题"的经验，再给它起名字，更容易理解，也知道它为什么存在。

**什么时候不用**：概念是对已有事物的抽象（例如线性表），没有"问题 → 办法"的推导链，用[演绎式](#2-演绎式先点出概念再逐条讲)。

**骨架**
1. 问题页：用场景把问题具体化，页末放 `> **本节问题**：…`。
2. 推出办法：在图上一步一步做。每一步都有理由，比如"关系丢了，就记下来""不知道从哪开始，就另外记一个头"。
3. 命名：一句一个，回指图里的东西，例如"一格数据加一格地址，合起来叫一个**结点**"。
4. 收拢：一句话给出干净的定义，最好和前面的同类概念对仗，例如"一个链表，就是一串用地址连起来的结点，加上一个头指针"，对应"一个顺序表，就是一段连续的格子，加上一个长度"。
5. 回到开头的问题。

**范例**：2.9"放弃'相邻'约定"→"什么是链式存储"。

**要守住的点**
- 命名之后一定要有一句收拢的定义，否则概念散在叙述里。
- 推导的每一步要有真实的理由，不能是作者先知道答案、再挑出来的"观察"。

**否决过的写法**
- 先给定义、再举例子。对"办法"类概念，读者还没有经验，定义是空的（2.9）。
- 让读者从几个例子里"观察出"特点再命名。读者发现不了，不诚实（2.1）。这和本条的区别是：本条是推导，那是挑选。

**来源**：2.9（2026-10-07）。

## 2. 演绎式：先点出概念再逐条讲

**适合什么知识**：对已有事物的抽象，例如"这一行字可以看成一个线性表"。

**什么时候不用**：概念是解决问题的办法，用[推出办法再命名](#1-推出办法再命名)。

**骨架**
1. 先点出概念："这一行字可以看成一个**线性表**。"
2. 逐条讲要点，每条三步：特点 → 例子 → 程序为什么在乎。
3. 结尾回到问题。
4. 如果练习要用到概念页没演示过的判断，加一页例题，正例、反例都要有。

**范例**：2.1"什么是线性表"。

**要守住的点**
- 措辞说"可以看成"，不说"叫"。具体的东西不等于抽象模型。
- 要点名称全书一字不差，例如"一个接一个"。

**否决过的写法**：归纳式，也就是先观察特点再命名（2.1）。

**来源**：2.1。

## 3. 两种画法对照

**适合什么知识**：同一份数据有一种具体的画法和一种简化的画法，后面主要用简化的那种。例如格子图（按内存位置）和箭头图（按逻辑顺序）。

**骨架**
1. 先画具体的。
2. 再画简化的，标出它和具体那张的对应关系，例如方框下面标地址。
3. 点明"两张图是同一份数据的两种画法"，各按什么排。
4. 说清对应规则："地址格里的数字，就是箭头指向的那个结点的地址；改了数字，箭头就跟着变。"
5. 约定后面用哪种画法。

**范例**：2.9"什么是链式存储"末尾的箭头图。

**要守住的点**
- 简化图上仍然标地址，这样改地址格时数字和图一一对应。作者明确要求箭头图标地址（2.9）。
- 对照放在概念页末尾，不单独成页。

**来源**：2.9（2026-10-07）。

## 4. 概念讲完，立刻做出第一个实例

**适合什么知识**：刚讲完一种数据表示，要让读者马上看到"这个问题确实能被解决"。

**什么时候不用**：要讲的是通用操作的实现，用[一个问题，一步一图](#5-一个问题一步一图)。这里的实例只做一次，不追求通用。

**骨架**
1. 提出问题："能不能真的把这一行存下来？"画出要达到的样子。
2. 第一步定义类型，然后从空开始一步一步搭：每步一段代码、一张图。重复的步骤说"同理"，不再展开。
3. 读出来：用同样的"目标 → 步骤 → 一般化"写出读取的循环。
4. 给出完整、能运行的程序，写明输出。
5. 一句交代局限："这种写法只能演示，通用的操作是下一节的事。"

**范例**：2.3"例题：把cat放进顺序表，再读出来"；2.9"用C语言表示链表"和"输出链表"。

**要守住的点**
- 完整程序要用 gcc 编译运行过，输出写进正文。
- 省掉的东西（错误检查、释放）要一句话说明。

**否决过的写法**
- C 页只讲类型、不写能运行的程序，把造结点和遍历都推到实现节（2.9 第四稿，被第六稿取代）。读者看不到问题被解决。
- 概念节先讲取元素、插入、删除的机制（2.9 第二、三稿）。操作的机制放实现节，在"操作前和操作后"里讲一次。

**来源**：2.3；2.9（2026-10-09）。

## 5. 一个问题，一步一图

**适合什么知识**：过程性知识，也就是会改变数据状态的操作和算法，例如插入、删除、销毁、各种指令。这是把"会做"拆成"能自己想出来"的写法。

**什么时候不用**：只读不改的简单操作（如求长度），步骤和已经讲过的一样时，借用前面的一句话带过，不逐步画图。

**骨架**
1. **问题**：用场景提出，例如"光标在行首 `|cat`，敲 b"。画出操作前和要达到的样子，用一句"对照两张图，变了两处：……"点出差别。
2. **第一步……第N步**：段首加粗写步骤名，例如"**第一步：申请b结点**"。
   - 每步一到三行具体的代码，接着前面的例子写，具体的字符和地址直接写在注释里；
   - 紧跟一张这一步做完后的图，结点下面标出 prev、q；
   - 关键推理写在对应那一步，例如先后顺序为什么不能反。重要的规则单独加粗成句。
3. **写成函数**：从目标说起，把具体的换成一般的，注释和步数一一对应。见[先具体后一般](#7-先具体后一般)。
4. **其他情形**：见[情形由简到繁](#6-情形由简到繁不需要新代码的一句话并入)。

**范例**：2.11"在第0个位置插入结点""在中间位置插入结点"；2.12"删除第0个结点""删除中间的结点""销毁链表，把操作合起来"。

**要守住的点**
- 图和代码一一对应：这一步的代码改了哪个格子，这一步的图就只变那个格子。
- 每页只解一个问题。操作多就拆节，例如链表操作拆成了 2.10–2.12 三节。
- 骨架在第一个操作点出一次，后面照做，不再重复说明。
- 每段代码都要能跑：把分步代码接在前面的程序后面，用 gcc 编译运行一次。

**否决过的写法**
- 操作前、操作后两张图，加文字列出几步，再整段给代码（2.10 第二稿）。中间状态没有图，读者要自己在脑子里跑代码。
- 单独一页"把操作写成函数"讲方法（2.4）。方法要在具体问题里自然显出来。
- 过程性内容套"例题N"格式（2.4）。怎么做本身就是要教的内容。

**来源**：2.9"用C语言表示链表"的写法被作者认可后推广（2026-10-09）；2.10–2.12。

## 6. 情形由简到繁，不需要新代码的一句话并入

**适合什么知识**：一个操作按位置、条件分几种情形。

**骨架**
1. 先讲最简单的情形，例如插在第0个：三步，不用走路。
2. 再讲多一步的情形，例如插在中间：只多一步"找到前一个结点"，其余说"同理"。
3. 套用已有代码就对的情形（如插在末尾），一句话并入，点出原因："都是插在某个结点后面，只是后一个恰好是 NULL"，并得出"三种其实是两种"。
4. 合成完整函数：用 if 把特殊情形分出来。

**范例**：2.11 插入、2.12 删除。

**要守住的点**：并入的那句话要说清"为什么不用新代码"，不能只说"同理"。

**否决过的写法**
- 先讲一般情形（中间）、再查两头。这在"整段给代码"的写法下可以，在一步一图的写法下，由简到繁更顺（2.11）。

**来源**：2.11、2.12（2026-10-09）。

## 7. 先具体后一般

**适合**：所有"从例子得出通用代码"的地方。

**骨架**
1. 用具体数值说每一步，例如"a 结点的地址格从 105 改成 102"。
2. 把具体值换成代码里的名字：a 结点是 prev，102 是 q，105 是 `prev->next`。
3. 从目标说起写成函数，例如"要删的是第i个结点，第一步先走i−1步，到它前一个结点。因此第i−1个和第i个结点都要存在才能删除"。

**要守住的点**
- 每个操作最后都要有一句一般化的话，否则读者会以为代码只对这个例子成立。
- 不写"'走1步'一般是走i−1步"这种要读者回头对照的句子（2.12）。

**来源**：2.10–2.12（2026-10-09）。

## 8. 语法细节放说明框

**适合**：正文代码里有读者第一次见的语法，但它不是这一页的主线。例如 `*L` 为什么带星号、`struct Node` 为什么写两遍、`LinkList` 其实是 `Node *`。

**骨架**
1. 正文只讲和图对应的东西："数据格是 data，地址格是 next，箭头就是 next。"
2. 每个细节各放一个 `::: tip 标题` 框，紧跟在代码后面，标题直接说结论，例如"LinkList：就是Node \*"。
3. 主线必须用到的事实，正文里留半句，例如"LinkList 是指向结点的指针类型"。

**要守住的点**
- 练习要考的东西如果在框里，框要在同一页、显眼。
- 选讲内容用 `::: tip`，易错点用 `::: warning`，主线内容不放框。

**否决过的写法**
- 画参数传递图讲 `*L`（2.10 第一稿）。这不是这一页的目标，放框里用两三句接上 2.5 就够。
- 把细节直接写在正文里，导致正文变长、主线被打断（2.9 C 页）。

**来源**：2.9、2.10（2026-10-09）。

## 通用措辞（所有写法都适用）

- 说"返回"，不说"交回"；需要名词时说"返回值为0"。
- 页标题和段首说全对象："删除第0个结点"，不说"删除第0个"。
- 术语全书一字不差："结点"，不用"节点"。
- 一稿两用：一段一件事，句子短，交叉引用单独成句，以后能直接当配音讲稿。
- 更多见 `docs/ch02-revision-guide.md` 第三部分。
